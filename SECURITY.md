# VÉRIX Security Policy

## 1. Repository MUST be private

The VÉRIX source repository **must remain private**.

While the repository is public, anyone can download the full clear-text `verix-app.html` and `admin_v2.html`. Client-side obfuscation becomes almost useless if the original source is public.

**Action required (do this now):**
1. Go to the repository → **Settings** → **General** → **Danger Zone**
2. Change visibility to **Private**

After making it private, only the production assets generated by the secure build should ever be published.

## 2. Client-side security model

The browser client is treated as an **untrusted environment**.

Client-side protections (obfuscation, domain lock, self-defending code, debug protection, disabled console) raise the cost of reverse-engineering. They are **not** a trust boundary.

All real authorization and sensitive logic must stay server-side:

- short-lived signed tokens (`verix-gate-v1`)
- build identifier validation
- origin checks
- rate limiting
- ASF / external service relays (never call them directly from the browser with secrets)
- admin authentication (`admin-auth-v2`)

## 3. Production release process

Never publish the HTML files that live in the repository root.

```bash
npm install
npm run build:secure          # or: npm run release
```

This produces a `dist/` folder containing:

- obfuscated `verix-app.html`
- obfuscated `admin_v2.html`
- lightweight entry points (`index.html`, `verix-mobile.html`)
- `build-manifest.json` (build ID + SHA-256 hashes)

**Publish only the contents of `dist/`.**

Recommended domains (already locked in the obfuscator):

- `https://verix.vxops.workers.dev`
- `https://verix-plataformadigital.github.io`

## 4. What the secure build does

- Control-flow flattening
- String array + base64 encoding + shuffle/rotate
- Self-defending code
- Debug-protection interval
- Console output disabled
- Domain lock (redirects to `about:blank` outside allowed hosts)
- No source maps
- Unique `build_id` for gate validation

Obfuscation increases reverse-engineering cost. It does **not** make JavaScript confidential.

## 5. Secrets — never in the client or repository

Never commit or embed:

- Supabase service-role keys
- `VERIX_ADMIN_PASSWORD` / `VERIX_ADMIN_SECRET`
- `VERIX_GATE_SECRET`
- any API credentials or private certificates

Store them only in Supabase / Cloudflare / GitHub Secrets.

## 6. Windows portable host

The Windows host already:

- disables DevTools and the default context menu
- blocks navigation outside the official domain
- blocks downloads and new windows to external sites

Keep shipping only the WebView2 host; never ship clear-text HTML inside the Windows package.

## 7. Incident response

If a build, credential, or authorization mechanism is suspected compromised:

1. Revoke the affected build ID (server-side)
2. Rotate the affected secret (`VERIX_GATE_SECRET`, `VERIX_ADMIN_SECRET`, …)
3. Invalidate active client / admin tokens
4. Generate and publish a new clean build from the private repository
5. Review telemetry and logs for abuse

Do **not** disclose a newly discovered credential in an issue, PR, commit message, or chat.

## 8. Hard limits of client-side protection

Anyone determined enough can still:

- capture network traffic
- debug a running session
- reconstruct logic from the obfuscated code given enough time

Therefore the real protection is:

1. **Private source repository**
2. **Server-side enforcement** (gate, rate limits, origin checks, no secrets in the client)
3. **Obfuscated production assets only**
